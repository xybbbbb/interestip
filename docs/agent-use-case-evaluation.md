# AI Agent Use Case & Evaluation

**案例：兴趣驱动旅行助手（Interest-Driven Travel Assistant）· CORTIS × Seoul**
一句话：把粉丝"我想去看演唱会、顺便打卡他们去过的地方"这种模糊需求，变成一份**有据可查、时间可行**的旅行行程。
本文记录它的 use case 定义、评估设计（18 个测试 case）与 5 轮迭代过程。

> English version: [`agent-use-case-evaluation-en.md`](agent-use-case-evaluation-en.md) · 线上原型：https://xybbbbb.github.io/interest_trip/ (EN / 中文)

## 1. Use Case：一个真实场景

**用户**：准备去首尔看 CORTIS 演唱会的人（不是"游客"，是"粉丝"）

**她的原话**：

> 我想去看他们的演唱会，也想去他们去过的地方打卡，顺便在首尔玩几天。

**她要的不是"攻略"，而是三件事**：

1. 哪些地方值得去、**为什么**（不能是"网上都这么说"）
2. 这些地方**能不能塞进我的天数里**（时间上真的走得到）
3. 演唱会那天**别安排别的**（19:00 必须到场）

**传统攻略为什么不够**：粉丝地点（MV 拍摄地、同款餐厅、快闪店）散在社区帖子里，
信息碎片化、置信度不一，而且地理上东一处西一处——照抄攻略的结果通常是"一天跑三个区、路上耗掉四小时"。

## 2. Agent 设计

```
用户一句话
   │
   ├─ ① 语料层   25 个地点，每个都带：来源链接、来源类型、发布时间、置信度、人工核验状态
   │
   ├─ ② 检索层   BM25 关键词检索（中文按双字切词）→ Top-K + 相关性阈值（"找不到就返回空"）
   │
   ├─ ③ 回答层   把 Top-K 拼成带 [来源n] 的回答；
   │             低/中置信度证据必须写成"有粉丝提到、尚未核验"，不许写成肯定句；
   │             检索为空 → 直接拒答（"资料里没有"）
   │
   └─ ④ 排程层   确定性算法（地理聚类分天 → 最近邻 + 2-opt 排序 → 硬约束校验）
                 · 演唱会日 19:00 锁定     · 18:30 后不再排景点
                 · 装不下的点进"待定清单"（不丢点）
                 · 站点间耗时用真实公共交通数据（102 组真实耗时）
```

**为什么这算 Agent 而不是普通程序**：③ 和 ④ 之间有一次**自我判断**——
"我手上的资料够不够支撑一个推荐？不够就该说不知道"。这正是 Agent 最容易翻车的地方
（检索失败还硬答），也是本文评估的重点。

## 3. 评估设计：18 个 case

### 为什么这样切

| 组 | 数量 | 考什么 | 为什么必须有 |
|---|---|---|---|
| **A 组**：证据检索与回答 | 12（9 可答 + 3 负例） | 能不能找到对的资料、该拒答时拒不拒 | 负例是灵魂：**问语料里没有的事，必须说"不知道"** |
| **B 组**：边界探针 | 3 | 口语改写、范围限定、专有名词 | 用户不会用"语料里的词"提问 |
| **C 组**：行程工作流硬约束 | 3 | 19:00 锁定 / 18:30 后不排点 / 不丢点 | 推荐再准，行程不可执行等于零 |

### B 组 · 边界探针（3）

| # | 问题 | 期望 | 实际 | 结果 |
|---|---|---|---|---|
| p01 | 想找个地方吃东西 | 餐厅/市场类地点 | **拒答** | ❌ 已知短板 |
| p02 | 同款餐厅（限定只在粉丝点里找） | 直火匠人等 | 直火匠人 龙山店 | ✅ |
| p03 | 乙支路煤炭烧烤在哪？ | 金浦高村店 | 同左 | ✅ |

### C 组 · 行程工作流硬约束（3，在 3 个行程场景下都要成立）

| # | 断言 | 结果 |
|---|---|---|
| W1 | 演唱会日 19:00 必须锁定在场馆 | ✅ 3/3 场景 |
| W2 | 演出日 18:30 之后不再排景点（并按**真实耗时**复核到达时间） | ✅ 3/3 场景 |
| W3 | 装不下的地点进「待定清单」，不丢点（25 个点一个不少） | ✅ 3/3 场景 |

### 四个指标怎么算

| 指标 | 定义 | 为什么用它 |
|---|---|---|
| **检索命中率** | 期望来源出现在 Top-5 的比例（9 道可答题） | 检索不到，后面全错 |
| **引用正确率** | 回答里挂的 `[来源n]`，有多少条真的属于期望来源 | 直接对应"有没有引用错资料" |
| **拒答正确率** | 3 个负例是否正确拒答 + 9 个可答题是否被误拒答 | **Agent 最容易翻车的地方：不知道却硬答** |
| **case 通过率** | 每个 case 只有"对/错"，取通过比例 —— 迭代表里用 A+B 两组（15 个，C 组不随检索改动变化），对外口径用 18 个 | 便于对外沟通的单一数字 |

## 4. 五轮迭代（每轮只改一件事）

| 轮次 | 发现的问题 | 改了什么 | 检索命中率 | 引用正确率 | 拒答正确率 | case 通过率 | 采纳？ |
|---|---|---|---|---|---|---|---|
| **R1** | 起点实现：BM25，中文按单字+双字切词、无阈值 | — | 100% | 73% | 75% | 80% | — |
| **R2** | 单字（"星/求/手"）造成大量误命中 | 只切双字 + 加相关性阈值 `max(1.5, 最高分×0.35)` | 100% | 79% | 92% | 87% | ✅ |
| **R3** | 硬负例「米其林三星餐厅求婚直升机」只靠"餐厅"一个词就命中 → **硬答** | 加 `minimum_should_match`：查询里超过 2 个词时，文档至少命中 **2 个不同词**才算候选 | 100% | **85%** | **100%** | **93%** | ✅ |
| **R4** | 口语改写「想找个地方吃东西」0 命中 | 加一张很小的同义词表（吃东西→餐厅/小吃/市场…） | 100% | 65% ↓ | 92% ↓ | 87% ↓ | ❌ **被评估集否决，回退** |
| **R5** | R4 的扩展把弱相关文档也带进来了 | 退回 R3 的检索策略，另试"只引用分数 ≥ 最高分 50% 的来源" | 100% | 83% ↓ | 100% | 93% | ❌ **无净收益，不采纳** |

### 这两轮被否决，是这份评估最有价值的部分

- **R4**：同义词扩展听起来完全合理，它确实修好了口语改写，但**把硬负例也一起救活了**——
  系统开始对"米其林三星求婚直升机"这类语料里根本没有的问题给出建议。对一个旅行助手来说，
  **编造一个不存在的推荐，比说一句"资料里没有"糟糕得多**。拒答正确率 100% → 92%，直接否掉。
- **R5**：R4 的教训是"召回换来了精度损失"，于是换了个思路——在引用这一步收紧。
  结果引用正确率 85% → 83%：门槛把一条**正确**的来源挤掉了。承认"没帮上忙"，不采纳。

> 如果不是先有评估集，这两轮都会被当成"优化"发布出去。

## 5. 最终结果

- **18 个 case 通过 17 个（94%）**：A 组 12/12 · B 组 2/3 · C 组 3/3
- 检索命中率 **100%** · 引用正确率 **85% → 100%**（接入大模型后，见第 6 节） · 拒答正确率 **100%**
- 引用结构自检：回答里的每条 `[来源n]` 都来自真实检索结果，**没有凭空造来源**

**已知短板（诚实记录，不藏）**

1. **口语改写**：`想找个地方吃东西` 仍然 0 命中。关键词检索的固有边界，同义词表补不干净——
   这正是下一轮要引入大模型/向量检索的理由（**它现在是一个有证据的结论，不是一句猜测**）
2. **排序噪声**：引用正确率 85% 的失分来自 Top-K 里混进的弱相关项（问手串时带出快闪店），
   需要 reranker 或更好的相关度模型
3. **样本量**：18 个 case 够发现"量级问题"，不足以做细颗粒度对比，后续扩到 30+

## 6. 接入大模型之后：提示词迭代（RAG 第 3 步）

生成层从「模板拼装」换成真实模型（DeepSeek `deepseek-chat`，OpenAI 兼容接口），**检索层完全不动**——
这样指标的变化才能干净地归因到生成层。

| 生成方式 | 检索命中率 | 引用正确率 | 拒答正确率 | case 通过率（A+B） |
|---|---|---|---|---|
| 模板版（基线） | 100% | 85% | 100% | 14/15 |
| 模型版 · 提示词 v1 | 100% | **100%** | 83% ↓ | 12/15 |
| 模型版 · 提示词 v2 | 100% | **100%** | **100%** | 14/15 |

### 第一轮（v1）暴露了两个问题，一个是提示词的，一个是我自己的

1. **模型过度拒答**：`MV 拍摄地的地铁站怎么打卡？` 明明检索到 3 条（新沙站、汉南站、首尔儿童公园），
   模型却回了一句"资料里没有能回答这个问题的内容"。原因是它拿"资料能否覆盖问题的每个细节"当标准：
   用户问"怎么打卡"，资料只写了"这里是 MV 拍摄地"，它就觉得证据不够。
2. **我的判定写错了**：`金浦那家烧烤店值得专门跑一趟吗？` 模型其实答得很好（引用了"不在首尔市区、
   需单独安排往返"），只是结尾补了一句"资料里没有能判断是否值得跑一趟的内容"，被我的关键词判定
   算成了拒答。**这是测量工具的 bug，不是模型的问题**——已改成"没有给出任何带来源的结论，才算拒答"。

### 第二轮（v2）改提示词：把判断标准从"资料是否完整"换成"资料是否相关"

> A. 资料里有与问题相关的地点 → 必须推荐出来并说明资料里写了什么，哪怕资料没覆盖问题的每个细节
> B. 资料与问题完全无关（只是碰巧出现了同一个词）→ 才拒答

结果：引用正确率保持 100%、拒答正确率回到 100%，通过率 12/15 → 14/15。

### 结论

- **模型接管生成层后，引用正确率从 85% 升到 100%**：模板会把 Top-K 里所有来源都挂上（包括弱相关项），
  模型只引用真正支撑结论的那一条
- 但引入了一个**新的失败模式：过度保守**——它比模板更容易说"资料里没有"。这类问题只能靠提示词迭代解决，
  而**评估集正好能把"改了提示词之后到底变好还是变坏"量化出来**（这次是 83% → 100%）
- 成本：一次完整评估 = 11 次调用、约 5.3k 输入 + 0.6k 输出 tokens（DeepSeek 价格下不到 1 分钱）

**还没做的**：模型目前在**命令行 / 构建期**跑（`scripts/rag-generate.mjs`）。静态页面 `index.html` 不能放 Key，
要把它搬进产品只有两条路——构建期预生成，或上 `TECH_BACKLOG` 的 **T4 最小后端**。

## 7. 下一步（接入大模型之后怎么继续）

这一轮评估覆盖的是"检索 + 引用 + 拒答"这三层；接入大模型之后，同一套 case 直接复用，
把"模板回答"换成"模型生成"，重点看两件事：

1. **新增 case 类型**：证据冲突时怎么办、多轮追问、跨城市扩展 —— 现在的 18 个 case 还没覆盖
2. **把模型搬进产品**：构建期预生成"推荐理由"，或上最小后端（T4）让页面实时调用
3. **升级检索**：第 ⑤ 步的 BM25 vs 向量检索对照，目标是把 `想找个地方吃东西` 这类口语改写救回来

## 8. 复现方式

```bash
cd outputs/interest-mcp
node scripts/agent-case-check.mjs          # 18 个 case 的通过情况 → data/agent-case-report.json
node scripts/rag-iterations.mjs            # 5 轮迭代对照表 → data/rag-iterations.json
node scripts/rag-eval.mjs                  # 当前配置的详细报告
node scripts/rag-eval.mjs --show-answers   # 额外打印每题的回答与引用
node scripts/benchmark-travel-model.mjs    # 行程层：真实耗时 vs 直线估算（含 C 组断言）

# 接入大模型（需要 .env 里的 LLM_API_KEY，DeepSeek 等 OpenAI 兼容接口都行）
node scripts/rag-generate.mjs "想买 CORTIS 同款的手串"        # 单次：检索 + 模型生成
node scripts/rag-eval.mjs --generator llm --prompt v2         # 模型版完整评估 → data/rag-eval-report-llm-v2.json
node scripts/agent-case-check.mjs --generator llm --prompt v2 # 模型版 18 case → data/agent-case-report-llm-v2.json
```

数据与代码：`data/rag-eval-set.json`（题面）· `data/agent-case-report.json`（18 case 结果）·
`data/rag-iterations.json`（5 轮指标）· `scripts/lib/rag.mjs`（检索 + 两道闸门）·
`scripts/lib/rag-answer.mjs`（回答组装层，接模型时替换这里）· `scripts/lib/rag-eval-core.mjs`（评估内核）

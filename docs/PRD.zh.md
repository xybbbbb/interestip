## 1. 一句话

告诉它你喜欢什么。它去找和这个兴趣相关的地点，把每条说法的可信度摊开，再排成一份你真的走得完的行程——围绕你已经订好、改不了的那件事。

## 2. 问题与洞察

**洞察：** 人很少是"去某个城市"，而是**因为某件事**去。当这件事成立时，难的不是找景点：

- 和这个兴趣相关的地点散在粉丝帖、MV、采访、博客和社交媒体里，可信度天差地别，而且完全没有结构。
- 一旦手里有了这份清单，第二个问题立刻出现：怎么把它变成走得动的行程，还要绕开一个改不了的时间点，又不把旅行毁掉。

**现成的替代方案为什么不行**

| 替代方案 | 哪里崩 |
|---|---|
| 通用 AI 旅行规划 | 按"热门"优化，兴趣本身——出门的理由——被稀释掉 |
| 自己列清单手动排 | 变成打卡清单：地理上荒唐，也没有留给城市的时间 |
| 直接搜社交媒体 | 没结构、没法核实，分不清是确认过的地点还是传言 |

**我们押的注：** 把**证据**当成一等数据结构（每个地点带来源 + 时间 + 置信度），把排程交给确定性代码而不是模型。这样"有个人色彩"和"真的走得完"才能同时成立。

## 3. 目标用户

**主要用户（v1）：因为某个兴趣而出行、并且已经有一个改不了的时间点的人。**
第一个案例：飞首尔看 CORTIS 演唱会、同时想去成员去过的地方、还想正常旅行的粉丝。

这类用户有三个特征，需求基本都是从这里长出来的：

1. **一个固定锚点。** 有件已经订好的事挪不动，其他安排必须绕开它。
2. **一长串又乱、又没有结构的候选地点。** 手里有 20–100 个"想去"，但判断不出哪个值得去。
3. **他们仍然想要一次真正的旅行。** 兴趣是出行的理由，不是行程的全部。

**次要用户：** 任何因兴趣出行的人——影视取景、美食、咖啡馆路线、徒步。同样三个特征，换一套内容。第二条垂直线（纽约 · 艺术与文化）存在的意义，就是把这句话从"说法"变成"验证过"。

## 4. 定位

```text
常规：  目的地 → 地点 → 行程
我们：  兴趣 → 关联地点 → 目的地 → 约束与偏好 → 个性化旅程
```

我们刻意不在"覆盖广度"上竞争。"你们支持哪些城市"是一场我们必输、而且不想被问的比赛。我们想被问的是：

- 这份行程理解你**为什么**去吗？
- 每条推荐从哪来的，看得见吗？
- 在你那个改不了的时间点面前，它真的走得完吗？

## 5. 产品原则

这些是决定其他一切的东西；功能打架时，就是靠它们裁决的。

1. **行程由一件改不了的事锚定。** 产品问的第一个问题不是"你想去哪"，而是"你已经订了什么"。锚点是**硬约束**不是偏好——演唱会 19:00 开演，那天的安排就得在开演前收尾；博物馆 10:30 定时入场，那天就从它开始排。
2. **是优先级栈，不是一堆点。** P0 锚点（锁定）→ P1 兴趣相关地点 → P2 普通观光。这既是排程顺序，也是在告诉用户这个产品在意什么。
3. **兴趣应该点亮旅行，而不是劫持它。** 普通观光是一等公民。如果排出来的东西没有吃饭、休息、随便逛逛的余地，那就是产品失败了。
4. **证据是数据结构，不是感觉。** 每个地点带来源、时间和置信度。置信度会改变界面怎么说话、以及这个地点怎么被安排——单一来源会被明确标出，低置信度可以一键隐藏。
5. **AI 干语言，代码干算术。** 模型负责：理解意图、把杂乱素材整理成结构化记录、写"为什么推荐这里"那一句。代码负责：距离、耗时、营业时间、路线可行性、地理聚类。**绝不让模型做这趟行程的算术。**
6. **答不上来就说"不知道"。** 语料撑不住的问题必须拒答。一个会编造地点的旅行助手，比一个承认自己不知道的更糟。
7. **候选数据永远标着候选。** 没有任何一条会从"看起来对"被悄悄升级成"已核验"。

## 6. v1 实际做了什么

```text
用户用一句话说出动机
  → 产品摊开自己的优先级：P0 锚点 → P1 兴趣地点 → P2 普通观光
  → 用户翻候选地点（带来源与置信度），标"必去 / 顺路"，观光点多选
  → 用户设硬约束：天数、哪一天已预约、节奏、预算、到达/离开、住宿策略
  → 引擎生成逐日行程：地理聚类 → 最近邻 → 2-opt → 时间安排
  → 地图按天打点，每段给"真实路线 / 步行 / 估算"三态
  → 每个地点能打开抽屉，看证据链和原始来源链接
  → 手动调整：把某一项拖到别的天
  → 现场模式：一张当地语言的大字卡片 + 给司机/店员看的常用语
  → 全程中英双语
```

两条垂直线跑在同一个单文件原型里：**CORTIS × Seoul** 与 **纽约 · 艺术与文化**。

## 7. 功能需求

| # | 需求 | 状态 | 验收标准 |
|---|---|---|---|
| R1 | 自然语言输入动机 | ✅ | 一句话动机能产出优先级栈和候选池 |
| R2 | 锚点作为硬约束，且随垂直线可配置 | ✅ | 演唱会 19:00（`last`）：之后不再排点；定时入场 10:30（`first`）：那天从它开始 |
| R3 | 每个地点带证据与置信度 | ✅ | 兴趣地点至少一条来源链接；单一来源会被明确标出 |
| R4 | 选择模型 | ✅ | 兴趣地点：必去 / 顺路；观光点：连续多选；**默认一个都不预选** |
| R5 | 约束表单 | ✅ | 天数、预约日、节奏上限、预算档、到达/离开、住宿策略都会影响结果 |
| R6 | 确定性排程 | ✅ | 同样输入产出同样行程；不出现不可能的路段（到达时间 vs 营业时间）；排不下的进"待定清单" |
| R7 | 真实耗时 | ✅ | 每段标注真实路线 / 步行 / 估算；没有覆盖的组合退回估算并明说 |
| R8 | 地图 + 按天视图 | ✅ | 总览与按天分色；点图钉出地点卡片 |
| R9 | 手动调整 | ✅ | 未锁定的项可以拖到别的天，不需要整份重排 |
| R10 | 现场模式 | ✅ | 当地语言大字 + 地址 + 常用语；语言跟随垂直线 |
| R11 | 中英双语界面 | ✅ | 中/EN 切换覆盖内容、标签和地图图例 |
| R12 | 生成的推荐语 | ✅ | 逐地点、逐语言，**构建期**生成并附上来源，不在打开页面时调用模型 |
| R13 | 会拒答的问答层 | ✅ | 必须有来源引用，否则拒答；用 18 个 case 的评估集度量 |

## 8. 明确不做（v1 的非目标）

预订、支付、实时价格、账号体系、服务端保存与分享、实时对话 agent、激进抓取社交平台、用户投稿地点、以及第三条垂直线。每一条自己都是一个产品；原型的任务是证明核心闭环。

## 9. 数据策略

| 层 | 来源 | 规则 |
|---|---|---|
| 兴趣地点（粉丝地点） | 公开资料策展，半自动收集 + 人工复核 | 每条保留来源和置信度；绝不当作"已核验"呈现 |
| 普通观光 | 官方开放数据（如 VisitSeoul OpenAPI） | 中英都用官方名称 |
| 地图与地点元数据 | OpenStreetMap | 必须署名（ODbL）；开放时间在核对到一手来源前算候选数据 |
| 站点间耗时 | Transitous（MOTIS） | 构建期查询，缓存成矩阵随仓库发布；运行时不依赖第三方 |
| 推荐语 | LLM，构建期生成 | 提示词里带上来源素材；API Key 不进客户端 |

**刻意的边界：** 不做激进抓取。数据来自官方 API、带人工复核的公开资料策展、以及用户投稿。机器只负责"提出候选"，什么算核验过，仍然由人决定。

## 10. 怎么判断它有效

v1 还没有用户数据——这是最大的缺口，也是下一个里程碑。要测的是：

| 想回答的问题 | 指标 | 目前读数 |
|---|---|---|
| 用户能自己走完流程吗 | 无需帮助就能生成出行程的测试者比例 | 尚未测（M5） |
| 行程真的可行吗 | 每份行程里"不可能的路段"数量 | 引擎测试中为 0 |
| 用户能信任一条推荐吗 | 已排地点中带来源链接的比例；路段中真实耗时（非估算）的比例 | 首尔 102 + 纽约 105 组，覆盖率 100% |
| 产品回答诚实吗 | 评估集上的拒答正确率 / 引用正确率 | 17/18 通过；引用正确率 85% → 100%（两轮提示词迭代后） |
| 它抓到"他的那趟旅行"了吗 | 定性：用户是否会把它说成"我的行程" | M5 收集 |

## 11. 垂直线策略

粉丝旅行是第一条线，纽约 · 艺术与文化是第二条。一条垂直线是**一次能力验证**，不是内容堆量：

> **只有当它能验证一个新能力时才加线，绝不为了"再多一个例子"而加。**

纽约线之所以够格，是因为它一次换了四件事：城市、兴趣、数据源（VisitSeoul → OpenStreetMap）、锚点语义（晚场演出 → 定时入场）。再来一个"美术馆城市"什么都证明不了。而影视线够格——它验证的是"一部作品 → 多个分散场景"，和"一个艺人 → 多个地点"是完全不同的数据形状。

一条新垂直线必须能提供：一种锚点类型、带逐条来源的地点池、这些地点之间的交通覆盖、以及所有支持语言的文案。

**被否掉的，以及为什么**（让上面那条规则有牙齿）：

- *咖啡 / 咖啡馆路线* —— 否掉。撑不起一天的兴趣会塌成"在咖啡馆待一天"，违反原则 3。判据不是"这个兴趣有没有意思"，而是"它能不能长出一个别人真的愿意过的一天"。
- *徒步 / 户外* —— 双重否决：交通假设不成立（登山口、公共交通覆盖薄弱），而且一条垂直线的质量上限就是策展人判断内容的能力。用自己看不懂的数据做出来的线，只会生产"自信的胡说"。

## 12. 风险

| 风险 | 为什么重要 | 怎么应对 |
|---|---|---|
| 粉丝说法在大规模上无法核实 | 核心价值主张**就是**可靠性 | 置信度分级、来源可见、单一来源与低置信度单独标注、任何升级前先人工复核 |
| 免费公共数据源会变或消失 | 原型依赖它们 | 全部在构建期缓存；耗时矩阵和地点数据随仓库发布 |
| 过度拟合粉丝场景 | "框架可复用"会变成没验证过的说法 | 刻意加入差异足够大的第二条垂直线 |
| 模型编造一条推荐 | 比承认不知道更糟 | 证据门槛、拒答是一等结果、每次改提示词都跑评估集 |
| 看着像进展的范围膨胀 | 多加一条线感觉很有产出，但什么新东西都没证明 | §11 的那条规则 |
| 用户分不清演示数据和核验过的数据 | 一旦发现，信任归零 | 候选数据在所有出现的地方都标着候选，包括页脚 |

## 14. 待回答的问题

1. "兴趣"到底是过滤器还是重排器？现在它定义候选池；也许更好的做法是把它当成对一次普通旅行的加权。
2. 一个行程能有几个锚点？锚点落在哪一天，由用户决定还是产品建议？
3. 让一个地点"值得排进行程"的最小证据集是什么？
4. 普通观光应该被自动补进来平衡一天，还是永远由用户显式选择？
5. 一趟旅行有两个兴趣时应该怎么表现——两个池子，还是一套混合排序？
6. 产品到哪里为止：生成行程，还是覆盖整趟旅行（现场模式是第一步）？
